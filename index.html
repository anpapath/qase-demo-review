🔴 Coverage Gaps 2 Untested scenarios that represent real risk
High Account lockout after repeated failed attempts
No test covers what happens after multiple consecutive failed logins. This is a security-critical path — without it, brute force protection is untested and a broken lockout mechanism would ship silently.
High Session expiry behaviour
No test verifies what happens when a user's session expires mid-workflow. Does the app redirect to login? Does it lose unsaved work silently? This is a common source of user-facing bugs that reach production.
🟡 Ambiguous Steps 2 Vague steps that produce inconsistent results across runs
Medium No assertion defined — step will always pass
TC-01 · Step 4
"Check that the page loads" has no pass/fail criterion. What constitutes a pass? The page rendering partially would satisfy this step. Suggest replacing with: "Assert that the dashboard heading is visible" or "Assert URL contains /dashboard".
Medium Expected result doesn't specify which error message
TC-03 · Expected Result
"Error message displayed" will pass even if the wrong error shows, or if the message leaks information (e.g. "Password incorrect" vs "Invalid credentials"). Suggest asserting the exact string — this also catches security regressions where error messages become too specific.
🟡 Missing Assertions 1 Steps that perform actions but never verify outcomes
Medium "Remember me" test has no session verification
TC-05 · Step 4
The test reopens the browser and checks the user is "still logged in" — but never asserts how. If the session cookie isn't persisted correctly but the app auto-logs in via another mechanism, this test passes and the feature is broken. Suggest asserting that the session token exists and matches the original.
🔵 Duplicates 1 Test cases covering identical scenarios — bloat without added coverage
Info TC-01 and TC-02 test the same scenario
Both test cases verify successful login with valid credentials. TC-01 uses "username and password", TC-02 uses "email and password" — but both follow identical steps and expected results. Merging them reduces suite maintenance overhead with no loss of coverage. If email vs. username login are distinct flows, they should be split into clearly differentiated cases with separate assertions.
